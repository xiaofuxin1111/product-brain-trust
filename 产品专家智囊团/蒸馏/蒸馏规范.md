# 蒸馏规范 v1.0

> 依据《The Mom Test》样张 v4 与你（用户）五轮评审的全部意见固化而成。
> 适用范围：剩余五本书的蒸馏、后续任何新增知识源的蒸馏、skill 运行时的话术生成。
> 违反以下任一条，该条判定项不予收录。

---

## 一、蒸馏单元：判定项（七字段）

每条判定项固定七字段，缺一不可。

| 字段 | 写作要求 | 反例 |
|---|---|---|
| **判定什么** | 一句话，说清这一条在查什么。内部视角，可用专业词 | ✗ "验证用户价值的成立性"（空泛）<br>✓ "他说的'需要'，是真遇到过，还是客气话" |
| **过关信号** | 什么样的回答算过关，必须可判定、可观察 | ✗ "用户表达了强烈需求"<br>✓ "他说出了具体时间、具体场景、具体损失" |
| **不过关信号** | 什么样算没过。这是全条的灵魂，比问法更重要 | ✗ "用户不理解"<br>✓ "全是'我觉得''应该会''大家都说'" |
| **小白版问法** | 用户嘴里会说的话，不用术语，不超两问 | ✗ "你的目标用户画像是什么"<br>✓ "你上一次因为这事烦，是什么时候？" |
| **答不上来怎么引导** | 降难度：给一个例子、允许说不知道、换更小的切口 | ✗ "请再想想"<br>✓ "比如你上周有没有因为找不到 XX，临时凑合了一次？" |
| **常见误判** | 小白在这一步最常犯的错，一句话点破 | ✓ "把朋友的'这个想法不错'当成需求验证" |
| **怎么解决** | 发现不过关后给用户的行动方案：3-5 步 + 每步一句为什么（用"为什么"或"（为什么：…）"标出） | 见下方"怎么解决"专项要求 |

### 「怎么解决」专项要求

1. **3-5 步，每步必须是动作**（问谁、问什么、看什么、写什么），不能是"思考一下""体会一下"
2. **每步配一句为什么**，一句话说完，不展开
3. **给时间刻度**（今晚 / 三天 / 一次对话），让用户知道成本
4. **最后一步要能产出可验证的东西**（一句原话、一个名单、一个数字），这样下次对话能复验
5. 案例**不写进对话话术**，只作为本字段的参考材料保留，并标注"仅供系统参考，对话不输出"

---

## 二、话术四条硬规则（不可违反）

1. **不造词、不造比喻**
   - 用普通人嘴里会说的词：说"解决方法"，不说"补法"；说"你要做的事"，不说"最小行动清单"
   - 不造"同一张底牌"这类比喻。宁可用大白话重复一遍，也不借比喻省字
   - 自检：这句话日常聊天里有人这么说吗？没有就改

2. **对话不举案例**
   - 不出现"书里说""有个案例""我见过一个人"——用户不知道你读过什么书，也不知道你凭什么"见过"
   - 判定项里的案例只供系统理解与人工核对忠实度，永不输出
   - 若觉得缺了案例说服力不够，就补一句"为什么"，不要补案例

3. **术语规则**
   - 术语可以出现，但出口的那句话里必须马上跟白话解释
   - 标准句式：`是否存在市场风险（说白了就是：有没有人真的要，愿不愿意掏钱）`
   - 一次回答里最多出现 1 个术语

4. **对话三段式**
   - 发现缺口后：**记缺口 → 给解决方法 → 讲为什么**
   - 不加案例、不加背景知识、不加勉励式套话
   - 单条输出控制在 6 行以内（不含编号步骤）

---

## 三、对话节奏规则

1. **交付不中断**：给完解决方法，明确"这事记你待办上，不耽误咱们接着聊"，**立刻抛下一个问题**
2. **禁止出现**"你去问完再回来""聊完再找我""等你准备好了我们继续"——这类表述会让用户以为对话已结束
3. **模块推进**：必答项全有答案就算过，"不知道"也算答案（记为缺口），不停留
4. **单轮提问**：一次 1 个问题，最多 2 个
5. **卡壳兜底**：同一问题两次引导仍答不上，标记缺口，不再纠缠
6. **全局兜底**：超过约 12 轮自动收尾；用户随时可喊停出报告

## 四、蒸馏合格线（自检清单）

每条判定项收尾前逐项过：

- [ ] 小白版问法能直接念出来，不拗口
- [ ] 不过关信号具体到"能听出来"，不是形容词
- [ ] 怎么解决的每一步都是动作，且有为什么
- [ ] 全条零书名、零术语裸奔、零生造词
- [ ] 和已有判定项不重复（同一判定信号只留一条）
- [ ] 能一句话说清"这条不过关会导致什么后果"

---

## 五、跨书去重规则

同一判定信号只保留一条。主口径优先级：

1. 能否让用户说出**具体事实**（The Mom Test 优先——事实骗不了人）
2. 能否暴露**代价**（俞军价值公式、启示录的机会评估）
3. 能否指向**下一步动作**（用户体验要素、人人都是产品经理）
4. 其余（上瘾的机制设计、启示录的组织流程）作为补充

冲突处理：保留判断更锋利的一条，另一条降为该条的"常见误判"或并入"怎么解决"。

## 七、踩过的坑（反例存档，勿重犯）

| # | 犯过的错 | 正确做法 |
|---|---|---|
| 1 | 用"补法""最小行动清单"这类自造词 | 说"解决方法""你要做的事" |
| 2 | 对话里写"书里有个故事" | 不提来源，不举案例 |
| 3 | 案例与用户当前问题不同类 | 不举案例，从根上避免 |
| 4 | 造"同一张底牌"式比喻 | 用大白话说完整，别省字 |
| 5 | 结尾"问完回来告诉我"让用户以为对话结束 | 记待办 + 立刻抛下一个问题 |
| 6 | 只蒸"判断"不蒸"方法"，用户知道有病没药 | 七字段必须包含怎么解决 |
| 7 | 把六本书做成六章目录端给用户 | 知识层前台不出现，只呈现缺口与解法 |
| 8 | 按"判断密度"选章，系统性漏掉全书最后一章的总结清单（《启示录》第 41 章、《The Mom Test》Cheatsheet 都是这么漏的） | 清单/总结类章节必读；每本书蒸完用作者自己的清单对一遍（见第八节） |
| 9 | 原文只有一句列举，却填了推测出来的案例 | 宁可不设案例，也不推测填充；标注"原文无展开" |

## 八、完整性校验：用作者自己的清单当尺子

**每本书蒸完，必须做一次清单式校验。** 六本里有三处作者亲手写的完整性清单，比凭感觉翻条目可靠：

| 书 | 清单位置 | 作用 |
|---|---|---|
| 《启示录》 | 第 41 章 产品经理的反省清单（十大问题） | 校验"一个产品该想清楚的全部"是否有洞 |
| 《The Mom Test》 | 第 8 章书末 Cheatsheet | 校验"验证流程"是否只蒸了判断、漏了做法 |
| 《用户体验要素》 | 五个层面本身即结构清单 | 校验层次是否齐 |

**校验方法**：把清单逐条对照知识地图，标四类状态——完整 / 部分 / 缺 / 合理舍弃。缺的补成条目，部分补充判定信号，舍弃的写明理由（便于验收）。

**判定"合理舍弃"的标准**：只有一种情况算合理——内容是给公司里上班的产品经理用的（团队协作、招聘、汇报、销售任务分配），个人做产品的人用不上。其余一律不许用"太细""用不到"当理由跳过。

**校验记录必须落盘**（写进合并总表的"清单式校验记录"一节），否则下次改版无法判断哪一版更完整。
